ASCENTIS CONSULTANT PORTAL - DATA FORMAT FOR THE POWER APPS REVIEWER SCREENS
=============================================================================

SOURCE TABLE
  Table:        asc_portalsubmission  (ConsultantDatabaseSolution)
  Environments: CDB Development  https://org84e19bfd.crm8.dynamics.com
                CDB Testing      https://org3db46cb7.crm8.dynamics.com
                CDB Production   https://org7fc54203.crm8.dynamics.com
  (same table and same JSON formats in all three; updated 24 Nov 2026 - see
   "WHAT CHANGED ON 23 NOV 2026" below)
  The Consultant Portal keeps ONE Draft row per consultant and tab and updates it on
  every Save draft; Submit turns that row into Submitted (see PART 2).

WHAT CHANGED ON 23 NOV 2026 (read this first)
  1. The portal NO LONGER WRITES THE LIVE TABLES. Save draft / Submit write only:
       - asc_portalsubmission  (one row per tab, JSON below),
       - asc_auditlog          (Update / Submit / AcknowledgeConfidentiality),
       - asc_attachment        (uploaded files only - a file cannot live in JSON).
     asc_consultant, asc_contact, asc_shareholder, asc_office, asc_projectreference,
     asc_operatorapproval (+ discipline/region rows), asc_bimproject, the financial/
     legal/ESG child tables and the consultant junction tables are written ONLY by the
     reviewer app when it Accepts. Accept = copy asc_after into the live tables.
  2. "liveId" in asc_after rows is now null for everything the consultant adds in the
     portal (the portal creates no live rows, so it has no GUID to stamp). Rows that
     came from a seeded/older submission keep the liveId they already had. Match on
     liveId when present; otherwise match on natural keys (contact email, shareholder
     name, operator name, project name, BIM project name) or create a new live row.
  3. Identity gains two keys when the consultant acknowledged the confidentiality
     statement in that session:
        "confidentialityAcknowledgedBy": "<display name>",
        "confidentialityAcknowledgedOn": "<ISO datetime, UTC>"
     The portal no longer writes asc_consultant.asc_confackn / asc_confacknby /
     asc_confackndate - copy these two values there on Accept if you need them.
  4. Attachments: files are asc_attachment rows (see "ATTACHMENTS" below). Project
     files have NO project lookup; they are tagged in asc_name as
     "<project name> | <file name>". The Attachments-tab JSON entries now also carry
     "projectName" for project files.
  5. A consultant who has no linked asc_consultant cannot save (the portal shows an
     error); it no longer creates a consultant row. Create/link it in the admin app.

COLUMNS
  asc_consultant_id     Lookup -> asc_consultant
  asc_tab               Choice (asc_consultantprofiletabchoice)
  asc_status            Choice (asc_powerpagestatuschoice)
  asc_before            JSON text - snapshot of the LIVE data when the row was created
  asc_after             JSON text - what the consultant entered (formats below)
  asc_submittedon       DateTime - set when submitted
  asc_reviewedby_id     Lookup -> systemuser (set by your review action)
  asc_revieweddate      DateTime (set by your review action)
  asc_rejectreason      Multiline text (required when rejecting)
  asc_isreview          Yes/No, required (portal always sends false)
  createdon             use it to find the newest row

CHOICE VALUES
  asc_tab:
    751050000 Identity (shown as "Overview")
    751050001 Financial
    751050002 Legal
    751050003 Offices & contacts
    751050004 Project references
    751050005 Operator approvals   (NEW)
    751050006 BIM
    751050007 Sustainability & ESG
    751050010 Attachments
  asc_status:
    751050000 Draft
    751050001 Submitted   
    751050002 Accepted
    751050003 Rejected
    751050004 Seeded      (written by the Power Apps seeding app; confirmed in a fresh export 2026-10-27)

RULES
  1. Review queue = rows with status Submitted (751050001).
  2. Per consultant and tab, the NEWEST row by createdon is what the consultant sees.
     Submitted, Accepted and Rejected rows LOCK that tab in the portal (read-only,
     status pill Pending / Accepted / Rejected). Draft and Seeded rows are editable.
     To let a consultant edit a tab again after review, write a NEW row for that tab
     with status Seeded (asc_after = the data to show). Newest createdon wins.
  3. Never edit or delete old rows - they are the history. (Only the PORTAL updates
     its own Draft row in place, until it is submitted.)
  4. Reject: status = Rejected, set asc_reviewedby_id, asc_revieweddate and a
     required asc_rejectreason.
  5. Accept: status = Accepted, then copy asc_after into the live tables
     (mapping: docs/portal-submission-automation-spec.md). Since 23 Nov 2026 the
     portal does NOT write the live tables, so Accept is the only thing that updates
     them. Set asc_reviewedby_id / asc_revieweddate as well.
  6. Do NOT change asc_after when accepting. The portal re-reads it as the starting
     point for the consultant's next edit.

asc_after FORMAT (a JSON string, one per tab)
  - Numbers and money are strings, e.g. "1000000".
  - Multi-select values are arrays of text (display names, not GUIDs).
  - Keys for conditional fields are MISSING when they do not apply.
  - "id" is a temporary form row id (e.g. "projects-3"); it changes between sessions.
    "liveId" is the real Dataverse GUID of an existing live row, or null (always null
    for rows the consultant adds in the portal - see change 2 above).
  - Values below are examples.

--- Identity (asc_tab 751050000) ---
{
  "firmName": "Studio Vermeer",
  "website": "studio.com",
  "firmType": "Private",
  "alias": "SV",
  "disciplines": ["Architecture"],

ATTACHMENTS (the actual files) - table asc_attachment
  The portal uploads each file as an asc_attachment row (+ the file in asc_attachedfile):
    asc_consultant_id   always set (the consultant)
    asc_name            "<file name>"  or, for a project file, "<project name> | <file name>"
    asc_filename        the file name
    asc_filesizemb, asc_uploadedon, asc_origin (self-service portal)
    asc_documenttype_id lookup (project files use "References")
    asc_projectreference_id  EMPTY for new project files (the portal creates no project
                        row). Set it yourself on Accept if you create the live project.
    asc_status          Draft (751050000) after Save draft; Submitted (751050001) after
                        Submit. Accepted/Rejected/Seeded are set by the reviewer app and
                        are never overwritten by the portal. A row with NO status (added
                        from the app) is shown to the consultant and can be removed by them.
    statecode           the consultant "removes" a file by DEACTIVATING the row
                        (statecode 1, statuscode 2); the portal lists active rows only.
                        Never hard-delete rows the consultant may still see.
  The portal reads asc_attachment rows of the signed-in consultant (asc_consultant_id)
  and, for the project popup, matches project files by the project name in asc_name.
  Files added by the reviewer app should therefore set asc_consultant_id (and, for a
  project file, name the row "<project name> | <file name>" with asc_filename = file
  name) so they appear in the portal.

asc_before FORMAT
  Same shape as asc_after, built from the LIVE tables when the row was created (so
  it shows what the reviewer app last wrote there).
  Difference: its contacts and bimProjects are { "liveId": "...", "fields": { ... } }
  instead of flat rows. Use it to compare against asc_after.

READING IT IN POWER APPS
  Set(j, ParseJSON(ThisItem.asc_after));
  Coalesce(Text(j.firmName), "")
  ForAll(Table(j.disciplines), Text(ThisRecord.Value))
  ForAll(Table(j.contacts), {Name: Text(ThisRecord.Value.firstName) & " " & Text(ThisRecord.Value.lastName)})
  Value(j.revenue1)
  Project references / Attachments are arrays: Table(ParseJSON(ThisItem.asc_after))

KNOWN GAPS
  - Attachments JSON holds metadata only (no file bytes); the files are asc_attachment rows.
  - Offices, Project references and Attachments cannot yet be copied into the live
    tables (asc_office.asc_officeleaderid mismatch; asc_ProjectType has no rows).
  - No server-side check blocks consultant edits once a row is Submitted.

=============================================================================
PART 2 - HOW THE PORTAL AND POWER APPS EXCHANGE DATA (SEEDING + REVIEW)
=============================================================================

END-TO-END FLOW
  1. Admin app creates the invited NATIVE Dataverse Contact (emailaddress1 = invitee's
     email) with its asc_consultantid lookup set to the consultant they may edit
     (this is NOT the asc_contact business-contact table).
  2. Admin app sends the Power Pages invitation (native "Invite contacts" feature).
  3. Admin app seeds the consultant's data: ONE asc_portalsubmission row PER TAB
     (9 tabs), see "SEEDING A ROW" below.
  4. Invitee redeems the link and signs in. The portal reads the signed-in contact's
     asc_consultantid, then loads the NEWEST asc_portalsubmission row per tab for
     that consultant and shows its asc_after in the form.
  5. Consultant edits and clicks Save draft -> the portal CREATES the tab's Draft row the
     first time and UPDATES that same Draft row on later saves (full tab JSON in
     asc_after; asc_before is set once, from the live tables, when the row is created).
     Submit for review -> that row's status becomes Submitted (asc_submittedon set), the
     tab becomes read-only in the portal ("Pending"), and the consultant's Draft files
     become Submitted. Nothing is written to the live tables.
  6. Reviewer app shows asc_before vs asc_after, then Accepts or Rejects (Part 1,
     rules 4-6). Accept copies asc_after into the live tables. The portal shows
     Accepted / Rejected tabs locked (status pill); to reopen a tab write a new
     Seeded row (rule 2).

WHAT THE PORTAL SHOWS PER TAB (newest row by createdon, any status)
  Draft      -> asc_after loaded, editable
  Submitted  -> asc_after loaded, LOCKED (pill "Pending")
  Rejected   -> asc_after loaded, LOCKED (pill "Rejected")
  Accepted   -> asc_after loaded, LOCKED (pill "Accepted")
  Seeded     -> asc_after loaded, editable (next save creates a new Draft row)
  The status is read when the page loads; a reviewer action shows after the
  consultant reloads / signs in again.
  no row     -> blank form
  If asc_after is empty or not valid JSON, that one tab simply shows blank.

SEEDING A ROW (what the Power Apps developer writes)
  asc_consultant_id   the consultant (lookup)                      REQUIRED
  asc_tab             tab number (751050000 ... 751050010)        REQUIRED
                      (751050005 Operator approvals added 15 Nov 2026)
  asc_status          751050004 (Seeded) when seeding existing     REQUIRED
                      data, so the tab opens editable.
                      Do NOT seed as Submitted: that locks the tab.
  asc_after           the tab JSON (formats in Part 1), as TEXT    REQUIRED
  asc_before          same JSON, or empty                          optional
                      (the portal never reads it; it is only for the reviewer's
                      comparison. Treat empty as "no earlier version".)
  asc_isreview        false                                        REQUIRED

  Power Fx example:
    Patch('Portal Submissions', Defaults('Portal Submissions'), {
      Consultant: ThisConsultant,
      Tab: 751050000,
      Status: 751050004,
      'Is Review': false,
      Before: jsonText,
      After: jsonText
    })
  (jsonText is a text variable holding the JSON; column/table names depend on how
   the table appears in Power Apps.)

RULES
  - Always create a NEW row; never edit or delete old rows. Newest createdon wins.
  - Seed all 9 tabs, or the missing ones show blank.
  - Keep keys exactly as in Part 1; a missing key shows blank.
  - "liveId" in seeded rows is optional now: the portal no longer writes live rows, so a
    missing liveId cannot create duplicates there. Keep it when you have it (it lets you
    update the right live row on Accept).
  - Use display names (not GUIDs) for choices/lookups, e.g. "region": "Europe".
  - Money/numbers are strings ("1000000"); multi-selects are arrays of text.
  - asc_after is a text column: build it with JSON() or by hand and write as text.
    NOTE: Power Fx JSON() turns a text table into [{"Value":"x"}]; the portal needs
    plain arrays like ["x"]. Build those arrays as text yourself (Concat).

BEFORE / AFTER WRITTEN BY THE PORTAL ITSELF
  asc_after  = that tab's slice of what the consultant has on screen when saving.
  asc_before = the same shape taken from the LIVE tables when the row was created.
               Its contacts/bimProjects are { "liveId", "fields": {...} } instead of
               flat rows. It is frozen at creation and never updated.

SECURITY / KNOWN LIMITS
  - Table permissions are Global scope: the portal's API returns all consultants'
    rows and filters to the signed-in consultant in the browser. Server-side
    isolation and a write-lock on Submitted rows are not built.
  - The portal does not write the live tables any more (since 23 Nov 2026); the reviewer
    app's Accept step is the only thing that copies asc_after into them.
  - asc_attachment permission is Global too: the portal lists only the signed-in
    consultant's files, but the API can return/update others'.
